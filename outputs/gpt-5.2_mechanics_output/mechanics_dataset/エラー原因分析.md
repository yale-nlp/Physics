# GPT-5.2エラー原因の詳細分析

## エラー状況の概要

### 現在の評価結果
- **総問題数**: 221問
- **成功**: 88問（39.8%）
- **失敗**: 133問（60.2%）← **問題**
- **平均精度**: 62.50%（成功した問題のみ）

### 失敗の特徴
- すべて`solution=null`（API呼び出し失敗またはレスポンス抽出失敗）
- `token_usage=null`（API呼び出しが完了していない）
- カテゴリ別の偏りなし（全体的に失敗）

## 根本原因の分析

### 1. 主要な原因：Responses APIのレスポンス構造の不一致

#### 問題の詳細

**現在のコード実装**（`evaluate_mechanics_gpt5_2.py` 127-173行目）:
```python
content = None
if hasattr(response, 'output_text'):
    content = response.output_text
elif hasattr(response, 'output') and response.output:
    # ネストされた構造に対応
    try:
        if isinstance(response.output, list) and len(response.output) > 0:
            output_item = response.output[0]
            if hasattr(output_item, 'content') and output_item.content:
                # ... 複数の形式を試行
    except Exception as e:
        print(f"Warning: Failed to extract content from response.output: {e}")
```

**問題点**:
1. **例外が発生していない**: エラーログファイル（`api_errors.log`）が存在しないことから、API呼び出し自体は成功している可能性が高い
2. **レスポンス構造の不一致**: 成功したエントリと失敗したエントリの違いから、レスポンス構造が期待と異なる可能性が高い
3. **reasoningパラメータ使用時の構造変化**: `reasoning={"effort": "high"}`パラメータ使用時、レスポンス構造が通常のResponses APIと異なる可能性

#### 成功例と失敗例の比較

**成功したエントリ**（例：`mechanics/1_9`）:
```json
{
  "id": "mechanics/1_9",
  "solution": "完全な回答テキスト...",
  "token_usage": {
    "prompt_tokens": 0,
    "completion_tokens": 0,
    "total_tokens": 1390
  }
}
```

**失敗したエントリ**（例：`mechanics/3_4`）:
```json
{
  "id": "mechanics/3_4",
  "solution": null,
  "token_usage": null
}
```

**重要な観察**:
- 成功したエントリでも`prompt_tokens`と`completion_tokens`が0になっている
- これは、Responses APIのレスポンス構造が期待と異なることを示している
- `total_tokens`は正しく記録されているため、API呼び出し自体は成功している

### 2. 考えられる具体的な原因

#### 原因A: reasoningパラメータ使用時のレスポンス構造の変化

**仮説**: `reasoning={"effort": "high"}`パラメータ使用時、Responses APIのレスポンス構造が以下のように変化している可能性：

1. **通常のResponses API**:
   ```python
   response.output_text  # 直接アクセス可能
   ```

2. **reasoningパラメータ使用時**:
   ```python
   response.output[0].content[0].text  # ネストされた構造
   # または
   response.output[0].text  # 別の構造
   # または
   response.text  # さらに別の構造
   ```

**証拠**:
- コードでは複数の形式を試行しているが、すべて失敗している
- デバッグ出力が標準出力に表示されている可能性があるが、確認できていない

#### 原因B: 非同期処理のタイミング問題

**仮説**: 非同期処理でレスポンスが完全に読み込まれる前に処理が進んでいる可能性

**証拠**:
- `asyncio.gather()`でバッチ処理を行っている
- バッチサイズが24と大きい
- 一部のリクエストがタイムアウトまたは不完全なレスポンスを返している可能性

#### 原因C: 画像入力によるプロンプトサイズの問題

**仮説**: base64形式の画像データが含まれるプロンプトが大きすぎて、レスポンス処理に影響している可能性

**証拠**:
- 力学データセットには画像が含まれている
- `_convert_to_responses_input()`関数で画像をbase64形式に変換している
- プロンプトサイズが大きい場合、レスポンス構造が変わる可能性

### 3. エラーハンドリングの問題

#### 現在の実装の問題点

**コード**（`evaluate_mechanics_gpt5_2.py` 174-203行目）:
```python
except Exception as e:
    error_str = str(e)
    error_type = type(e).__name__
    print(f"Attempt {attempt + 1} failed: {error_type}: {e}")
    
    # エラーログをファイルに記録
    try:
        error_log_path = os.path.join(os.path.dirname(__file__), "api_errors.log")
        with open(error_log_path, "a", encoding="utf-8") as f:
            # ... エラーログを記録
    except Exception:
        pass  # エラーログの記録に失敗しても処理を続行
```

**問題点**:
1. **例外が発生していない**: エラーログファイルが存在しないことから、例外は発生していない
2. **サイレント失敗**: レスポンスからコンテンツを抽出できない場合、例外を発生させずに`None`を返している
3. **デバッグ情報の不足**: レスポンス構造を確認するためのデバッグ出力が標準出力にのみ表示され、ファイルに保存されていない

## 推奨される修正方法

### 1. レスポンス構造の詳細なログ記録

**修正内容**:
```python
# レスポンス構造を詳細にログに記録
if content is None:
    debug_log_path = os.path.join(os.path.dirname(__file__), "response_debug.log")
    with open(debug_log_path, "a", encoding="utf-8") as f:
        f.write(f"=== Response Debug ===\n")
        f.write(f"Response type: {type(response)}\n")
        f.write(f"Response attributes: {dir(response)}\n")
        if hasattr(response, 'output'):
            f.write(f"Response.output type: {type(response.output)}\n")
            f.write(f"Response.output: {response.output}\n")
        f.write(f"Response dict: {response.model_dump() if hasattr(response, 'model_dump') else 'N/A'}\n")
        f.write("=" * 80 + "\n\n")
```

### 2. reasoningパラメータなし版との比較

**推奨**: `evaluate_mechanics_gpt5_2_no_reasoning.py`を実行して、reasoningパラメータが原因かどうかを確認

**確認事項**:
- reasoningパラメータなし版で成功率が向上するか
- レスポンス構造が異なるか

### 3. レスポンス構造の包括的な対応

**修正内容**: OpenAI SDKの最新バージョンとResponses APIのドキュメントを確認し、正しいレスポンス構造に対応

**可能性のある構造**:
```python
# パターン1: 直接アクセス
content = response.output_text

# パターン2: ネストされた構造
content = response.output[0].content[0].text

# パターン3: reasoningパラメータ使用時
content = response.output[0].text

# パターン4: 辞書形式
content = response.get('output_text') or response.get('output', [{}])[0].get('text')
```

### 4. タイムアウトとリトライロジックの改善

**修正内容**:
```python
# タイムアウトを明示的に設定
response = await asyncio.wait_for(
    client.responses.create(**create_kwargs),
    timeout=300  # 5分のタイムアウト
)
```

## 結論

**主要な原因**: Responses APIのレスポンス構造が期待と異なり、特に`reasoning={"effort": "high"}`パラメータ使用時に構造が変化している可能性が高い。

**根本的な問題**: 例外が発生していないため、エラーハンドリングでは捕捉できず、サイレントに失敗している。

**解決策**: レスポンス構造を詳細にログ記録し、実際の構造を確認してから適切な修正を実施する。
