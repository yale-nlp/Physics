# 要件定義書（現状分析ベース）

## 1. 背景 / 目的

本リポジトリは、大学院レベル（PhD予備試験相当）の物理問題ベンチマーク **PHYSICS** に対して、LLM の回答性能を **自動評価** するためのコードと成果物をまとめたもの。

評価の核は以下。

- LLM出力から **最終解** を `\boxed{...}` 形式で抽出する
- 予め用意された正解（データセット内の `final_answers`）と **同値性判定** を行い、正誤・スコアを集計する  
  - SymPy による数式同値判定 + 失敗/テキスト混入時の LLM フォールバック

## 2. 想定ユーザー

- 研究者/開発者（ベンチマーク評価を回したい人）
- 解析担当（モデル別の結果CSVやプロットを見たい人）

## 3. 対象範囲（スコープ）

### 3.1 スコープ内

- **データセット（JSONL）** を読み込み、問題文（テキスト + 画像）を LLM に提示する
- LLM の出力から `\boxed{}` を抽出し、正解と同値か判定する
- 1問ごとのスコアを保存し、全体精度（平均）等を集計して保存する

### 3.2 スコープ外

- 学習・ファインチューニング
- 問題作成/アノテーション生成
- RAG のためのコーパス構築（`api_evaluation` には検索があるが、コーパス管理は本リポジトリ外）

## 4. 入力 / 出力

### 4.1 入力（データセット）

- 代表ディレクトリ: `PHYSICS/`
- 形式: **JSONL（1行=1問）**

主なキー（例: `PHYSICS/atomic_dataset.jsonl` 先頭行より）

- `id`: 例 `"atomic/1-48"`
- `questions`: 問題文（テキスト）
- `solutions`: 解説（テキスト）
- `final_answers`: 正解配列（LaTeX/テキスト混在）
- `graphs`: 画像等の付加情報
  - 画像ありの場合: `[{ "type": "image_url", "image_url": { "url": "data:image/png;base64,..."}}]`
  - text-only の場合: `null` または `[]`

### 4.2 入力（LLMアクセス情報）

スクリプトにより異なるが、概ね以下が必要。

- `OPENAI_API_KEY`（OpenAI API / OpenAI互換API）
- `GEMINI_API_KEY`（Gemini OpenAI互換エンドポイントを利用するスクリプト）
- Together 等のキー（`api_evaluation/evaluate_r1*.py` など）

### 4.3 出力（評価結果）

既存成果物は `outputs/` 配下に多数存在し、モデル×データセット単位で以下のようなファイルが生成される。

- `response.jsonl`: 1問ごとの評価結果（**solution/抽出解/同値判定ログ/accuracy** を含む）
- `accuracy.csv`: 全体精度、分散、SymPy失敗→LLMで正解になった比率など（スクリプトにより列が若干異なる）
- `score.csv`: 1問ごとのスコア（accuracy）一覧
- `scatter_plot.png`: 1問スコア散布図

## 5. 機能要件

- **FR-1 データ読み込み**
  - JSONL を読み、`questions` と `graphs` を LLM の入力形式に変換できる
- **FR-2 LLM問い合わせ**
  - API（OpenAI互換含む）またはローカル推論（vLLM）で回答を生成できる
- **FR-3 最終解抽出**
  - LLM出力から `\boxed{...}` を抽出し、複数解（配列）にも対応する
- **FR-4 同値性判定**
  - 数式は SymPy で同値判定
  - テキスト混在/パース失敗/タイムアウト時は LLM で同値判定（フォールバック）
- **FR-5 集計**
  - 1問スコアと全体指標を保存する
  - 画像（散布図）を生成できる

## 6. 非機能要件

- **NFR-1 安定性**
  - SymPy の計算にタイムアウト（現状は `SIGALRM` を利用）
  - 例外時はスキップ/デフォルト（accuracy=0）で処理継続
- **NFR-2 並列性**
  - API評価: asyncio + batch
  - オフライン評価: `ProcessPoolExecutor`
- **NFR-3 再現性**
  - 生成結果（JSONL/CSV/PNG）がファイルとして保存される
- **NFR-4 コスト/速度**
  - API呼び出し回数、RAGの検索回数がコストに直結（運用上の注意が必要）
  - `graphs` に **data:image(base64直埋め)** が含まれる場合、1問あたりの入力が巨大化しやすい
  - 評価結果に **トークン使用量（prompt/completion/total）** を保存し、コスト見積り・異常検知ができること

## 7. 既知の問題点（現状）

- **ディレクトリ参照の不整合**
  - 多くのスクリプトが `datasets/...` や `text_only_dataset/...` を参照するが、リポジトリ上の実体は `PHYSICS/...`（例: `PHYSICS/PHYSICS-textonly/...`）
- **オフライン推論スクリプトの引数定義不足**
  - `offline_evaluation/get_answer.py` は `argparse` で引数を追加していないため、そのままだと `args.model_name` 等で失敗する可能性が高い
- **APIキー/URLのハードコード**
  - `your_api_key` / `Your Base URL` 等のプレースホルダが残っている
- **依存関係の重複**
  - `requirements.txt` に `sympy==1.13.3` と `sympy==1.13.1` が重複している
 - **画像付きデータセットのトークン肥大**
   - `PHYSICS/*_dataset.jsonl` の `graphs` は `data:image/...;base64,...` を含み、1問あたり数万文字の入力になりうる
   - `\boxed{}` 抽出失敗時に「同じ巨大入力を再送」すると、失敗ケースでトークン消費が跳ねるため注意が必要
