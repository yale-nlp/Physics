# 詳細設計書（現状分析ベース）

## 1. データ設計

### 1.1 データセット（JSONL 1行=1問）

配置:

- 画像あり: `PHYSICS/*.jsonl`
- text-only: `PHYSICS/PHYSICS-textonly/*_textonly.jsonl`

スキーマ（代表例）:

- `id: str`（例: `"atomic/1-48"`）
- `questions: str`
- `solutions: str`
- `final_answers: list[str]`
- `graphs: list[object] | null`

`graphs` 要素の代表:

- 画像:
  - `{"type": "image_url", "image_url": {"url": "data:image/png;base64,..."}}`

### 1.2 評価結果（`outputs/*/*/response.jsonl`）

API評価スクリプトが保存する `response.jsonl` は、実質的に「最終評価結果」になっている（生成回答も内包）。

- `id: str`
- `solution: str | null`（LLMの生回答）
- `final_answers: list[str]`（抽出された `\boxed{}`）
- `equivalency_results: list[object]`（比較ログ）
- `accuracy: float`（抽出解単位の正解率）
- `token_usage: object | null`（取得できた場合のトークン使用量）
  - `prompt_tokens: int`
  - `completion_tokens: int`
  - `total_tokens: int`

`equivalency_results` の代表スキーマ（`equation_equivilancy.is_equiv` の返却）:

- `input_expressions.expr1: str`（LLM抽出解）
- `input_expressions.expr2: str`（データセット正解候補）
- `preprocessed_expressions`: SymPy標準化した文字列（成功時）
- `sympy_result: bool | null`
- `llm_result: bool | null`
- `final_result: bool | null`
- `error: str | null`

### 1.3 CSV

- `accuracy.csv`: 全体精度等（列はスクリプトにより差異あり）
- `score.csv`: 問題IDと1問スコア

## 2. アルゴリズム設計

### 2.1 `extract_boxed.extract_final_answer_allform`

目的: LLM出力から `\boxed{...}` を抽出し、必要に応じて配列化する。

主要ポイント:

- 正規表現で `\boxed{...}` を全件抽出
- `answer_type='list'` の場合は `\boxed{[a,b,c]}` のような表現を分解し配列化
- 抽出できない場合は空配列（評価スクリプト側で失敗扱い）

### 2.2 `equation_equivilancy.is_equiv`

目的: 2つの LaTeX 文字列が「数理的に同値か」を判定する。

手順:

1. **テキスト混入判定**
   - `\text` が含まれる場合は SymPy を使わず LLM 比較に移行
2. **前処理**
   - 添字の簡易除去（`_x`, `_{...}` など）
   - `\left`, `\right` の除去、`\cdot` → `*` など
   - `A=B` の場合は RHS のみ抽出（比較を安定化）
3. **SymPyでの同値判定**
   - `parse_latex` → `simplify(expand(trigsimp(expr)))`
   - `simplify(expr1 - expr2) == 0` または `expr1.equals(expr2)`
   - `SIGALRM` によるタイムアウト（デフォルト10秒）
4. **フォールバック（LLM比較）**
   - SymPy が False/失敗/タイムアウトの際に LLM へ委譲し True/False を得る

注意点:

- `SIGALRM` は Unix 系依存（macOS/Linuxで動作、Windowsは要注意）
- LLM フォールバックはコスト増になる（特に SymPy 失敗が多い場合）

### 2.3 スコア計算（各 evaluate_*）

実装は概ね次の形。

- LLM抽出解 `flattened_answers` を走査
  - 各 `llm_answer` について、`dataset_answers` のいずれかと `final_result=True` になれば「当該抽出解は正解」としてカウント
- `accuracy = correct_count / len(flattened_answers)`（抽出解が0なら0）

#### boxed抽出失敗時の扱い（コスト最適化）

`graphs` に data:image(base64直埋め) が含まれるケースでは、**同じ入力（特に画像）を再送**するとコストが急増する。
そのため、`evaluate_mechanics_gpt4o.py` では以下を採用する：

- まず通常通りに解かせる（questions + graphs）
- `\boxed{}` 抽出に失敗した場合は、**前回の回答テキストのみ**を渡して「boxed形式へ整形」させ、再抽出する  
  （＝画像を再送しない）

## 3. 例外/エラー処理

- LLM呼び出し失敗: `solution=None`, `final_answers=[]`, `accuracy=0`
- `\boxed{}` 抽出失敗: 同上（失敗扱い）
- SymPyタイムアウト: `sympy_result=None`、その後LLM比較へ

## 4. ファイル単位の実装/運用計画（現状を踏まえた整理）

本リポジトリを「再現可能に動かす」ために、優先度順に以下の手当が必要。

- **`offline_evaluation/get_answer.py`**
  - `argparse` の引数（`--model_name`, `--download_dir`, `--output_dir`, `--max_lines`, `--dataset_list`）を定義
- **`offline_evaluation/evaluation.py`**
  - データ参照を `PHYSICS/` に合わせる（`dataset_dir` の既定値）
  - 出力先を `outputs/` と整合させる（既存成果物の整理方針に合わせる）
- **`api_evaluation/*`**
  - `datasets/` / `text_only_dataset/` を `PHYSICS/` / `PHYSICS/PHYSICS-textonly/` に統一
  - APIキーの取得方法を `.env` に統一（プレースホルダ撤去）
- **`requirements.txt`**
  - `sympy` の重複バージョンを解消

## 5. 既知の不整合（要件/基本設計への反映）

- スクリプトの参照パスと、リポジトリの実データ配置が一致していない
- `outputs/` は既に多数の成果物があり、実行スクリプトの出力仕様と完全一致しないケースがある  
  - 例: `outputs/gpt-4o_output/*/` では `final_evaluation.jsonl` は存在せず、`response.jsonl` が評価結果を内包している
